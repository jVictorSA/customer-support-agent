# Database Migration

Manage the Postgres schema through Alembic only. Never let the API create or
upgrade schema at startup.

Canonical contract: `.agents/project-context/architecture.md` and
`.agents/rules/persistence-and-migrations.md`.

## Guardrails

- Never run `alembic upgrade head` automatically in application startup or
  deploy scripts.
- Never edit an already applied migration; create a new revision.
- One migration equals one logical schema change.
- Always review the SQL generated by `--autogenerate` before applying it.
- Do not run migrations against production/hml from this workflow unless the
  user explicitly asks and confirms the target environment.
- Do not touch the development database for integration-test validation; use
  `customer_support_agent_test`.
- Do not invent primary-key or timestamp conventions; ask if the project has
  not decided them yet.

## Preconditions

1. The database container is running:

   ```bash
   docker compose up -d db
   ```

2. Every new ORM model is imported in
   `src/customer_support_agent/db/metadata.py`.
3. The model lives in `modules/<module>/infrastructure/persistence/models.py`
   and uses the shared `Base`.
4. The application tests pass before generating a migration:

   ```bash
   uv run pytest
   ```

## Workflow

```
Migration Progress:
- [ ] 1. Inspect current revision and model changes
- [ ] 2. Generate the revision with --autogenerate
- [ ] 3. Review the generated migration and SQL
- [ ] 4. Apply and verify
- [ ] 5. Verify downgrade (when safe)
- [ ] 6. Update docs and validate
```

### 1. Inspect

```bash
docker compose exec api alembic current
git diff -- src/customer_support_agent/db src/customer_support_agent/modules
```

### 2. Generate

```bash
docker compose exec api alembic revision --autogenerate -m "create products"
```

Use a short, imperative message describing the logical change.

### 3. Review

Open the new file in `alembic/versions/` and verify:

- Correct tables, columns, types, nullability, defaults, indexes, constraints.
- Foreign keys and delete behavior are intentional.
- The naming convention from `db/base.py` is respected (avoid hand-written
  duplicate constraint names).
- `down_revision` points to the current head.
- The `downgrade()` actually reverses `upgrade()`.
- Autogenerate did not miss or invent changes. If it did, fix the models or
  edit the *new, unapplied* migration; never edit an applied one.

### 4. Apply and verify

```bash
docker compose exec api alembic upgrade head
docker compose exec api alembic current
```

Then verify the schema or run the relevant integration test.

### 5. Downgrade check

For safe/applicable changes, confirm the down migration:

```bash
docker compose exec api alembic downgrade -1
docker compose exec api alembic upgrade head
```

Do not run a destructive downgrade against data you cannot recreate.

### 6. Validate and document

```bash
uv run pytest
docker compose up -d db
RUN_INTEGRATION_TESTS=1 POSTGRES_DB=customer_support_agent_test \
  uv run pytest -m integration
```

Update `README.md` and `.agents/project-context/architecture.md` if the schema
decision or migration procedure changes. Report the revision id, the applied change, and
the review result.

## Rollback

To undo the latest local revision in a development database:

```bash
docker compose exec api alembic downgrade -1
```

If a migration was already shared/applied elsewhere, do not rewrite it; add a
corrective migration instead.
